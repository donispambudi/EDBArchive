# Packing-method Benchmark

The repository includes a standalone benchmark for comparing the backup and
restore behavior of four packing methods: baseline, Carpov, Erkin, and
EDBArchive. The benchmark uses the same OpenFHE 1.4.0 build, BFV context,
MariaDB service, and seeded TPC-C database as the main deployment.

Context and key-pair generation are excluded from the measurements. All
methods reuse the context and key pair generated by the seeded jobs. Every
backup generates and bundles a relinearization key, matching the original
implementations. EDBArchive additionally generates and bundles the rotation
key required by its packing method.

## Scenarios

The benchmark provides two JSON workload configurations corresponding to the
shares prepared by `DatabaseSeeder`:

| Scenario | FHE-protected columns |
|---|---|
| `district` | `district.d_next_o_id` |
| `district-customer-item` | `district.d_next_o_id`, `customer.c_payment_cnt`, `item.i_im_id` |

The configuration files explicitly define the tables, primary keys, and
protected columns. The benchmark does not query the EDBArchive web metadata to
discover its workload. It reads MariaDB only for the actual TPC-C values and
for the backup and restoration operations being measured.

## Prerequisites

Complete [Installation and Setup](installation.md), start the main services,
and wait until all four seeded jobs have status `completed`. This ensures that
the context and key files exist and that no seeded backup job is competing for
CPU or database I/O while measurements are collected. The benchmark joins the
main `edbarchive_default` network and mounts its generated-artifact volume
read-only.

Build the benchmark image from the `benchmark/` directory:

```bash
cd benchmark
docker compose --env-file ../.env build
```

## Run the complete benchmark

From the `benchmark/` directory, choose one of the following commands.

### Option 1: default container user

```bash
docker compose --env-file ../.env run --rm benchmark scenarios
```

Depending on the host's Docker user-namespace configuration, files written to
`results/` may be owned by `root` or `nobody`. This does not affect the
benchmark, but changing or deleting the files from the host may require
elevated privileges.

### Option 2: current host user

On Linux, pass the current UID and GID so generated results belong to the
reviewer running the command:

```bash
docker compose --env-file ../.env run --rm \
  --user "$(id -u):$(id -g)" \
  benchmark scenarios
```

This changes only filesystem ownership. It does not change the database user,
OpenFHE operations, benchmark workflow, or reported measurements. If the
mounted FHE artifacts are not readable by the host UID, use Option 1 instead.
To recover ownership of results already produced by Option 1, run from the
`benchmark/` directory:

```bash
sudo chown -R "$(id -u):$(id -g)" results
```

This command runs all four methods for both scenarios, producing eight backup
measurements and eight corresponding restore measurements. Every backup uses
a temporary clone of the source `tpcc` database. Each generated bundle is
then imported and restored into a temporary target database to verify that the
restore path completes successfully.

### Quick run

To check the benchmark with lower storage and execution-time requirements, run
only the one-column `district` scenario. The same two user options apply. For
host-owned results, use:

```bash
docker compose --env-file ../.env run --rm \
  --user "$(id -u):$(id -g)" \
  benchmark quick
```

The quick command still compares all four packing methods, producing four
backups and four restores. It skips the larger `district-customer-item`
scenario.

## Temporary storage and free-space check

Restore extraction uses `benchmark/tmp/`, which is mounted into the container
as a host-backed temporary workspace. It is cleaned after both successful and
failed restores. To use a larger drive, create a writable directory there and
provide its absolute path when running the benchmark:

```bash
mkdir -p /path/on/large-drive/edbarchive-benchmark-tmp
BENCHMARK_TMP_DIR=/path/on/large-drive/edbarchive-benchmark-tmp \
  docker compose --env-file ../.env run --rm \
  --user "$(id -u):$(id -g)" \
  benchmark scenarios
```

Before running `district-customer-item`, either alone or as part of the full
suite, the runner checks free space on the configured bind mount:

- less than 65 GiB: the benchmark is cancelled before any scenario starts;
- 65 GiB to less than 97.5 GiB: a warning is printed and execution continues;
- 97.5 GiB or more: execution continues without a storage warning.

The 97.5 GiB recommendation applies a 1.5 safety factor to the 65 GiB estimate.
The quick `district` scenario is not subject to this large-scenario threshold.

During suite restoration, `bundle.tar.gz` is deleted after successful
extraction and `dump.sql` is deleted after import. Ciphertext files are then
removed incrementally, but only after the database commit covering their final
use succeeds. This prevents the compressed archive, complete extracted bundle,
and expanded MariaDB representation from remaining on disk simultaneously.

Successfully restored benchmark databases are removed by default. To retain
them for inspection, add `--keep-databases`. A stable result identifier can be
provided with `--run-id`:

```bash
docker compose --env-file ../.env run --rm benchmark scenarios \
  --run-id paper_run_1 --keep-databases
```

## Results

Results are written on the host under:

```text
benchmark/results/run_<UTC timestamp>/
├── summary.csv
├── district-baseline/
├── district-carpov/
├── district-erkin/
├── district-edbarchive/
├── district-customer-item-baseline/
├── district-customer-item-carpov/
├── district-customer-item-erkin/
└── district-customer-item-edbarchive/
```

After a successful suite run, each method directory contains its backup and
restore metrics. The uncompressed `bundle/` staging directory is removed after
archive creation. The `quick` and `scenarios` runners then record the
compressed bundle size, extract it for restore verification, and discard
`bundle.tar.gz` before MariaDB expands the restored representation. This
reduces peak storage and avoids retaining large benchmark artifacts that are
no longer needed. Individual backup and restore commands retain the archive by
default. `summary.csv` collects the following values:

| Column | Meaning |
|---|---|
| `scenario` | Workload configuration used by the run |
| `method` | Packing method |
| `backup_backend_ms` | Backup backend execution time |
| `backup_total_ms` | End-to-end backup time, including clone, dump, compression, and cleanup |
| `restore_backend_ms` | Restore backend execution time |
| `restore_total_ms` | End-to-end extraction, import, restoration, and cleanup time |
| `dump_bytes` | Size of the uncompressed SQL dump |
| `bundle_bytes` | Size of the final compressed bundle |

The backend timing boundary follows the standalone FHE backend. The
end-to-end measurements additionally include the surrounding database and
archive operations required to produce or consume a transferable bundle.
Each backup metrics file also records `tar_bytes` and `compression_level`. The
compression policy matches the main wrapper: `pigz -8` when `dump.sql` is more
than half of the uncompressed tar archive, and `pigz -1` otherwise.

For individual-method commands, custom FHE artifacts, and implementation
details, see the
[benchmark README](https://github.com/donispambudi/EDBArchive/blob/main/benchmark/README.md).
